# Tangled

[Tangled](https://tangled.org) is a forge built on the AT Protocol, the network Bluesky runs on. People are known by their handle (`tangled.org`, `oppi.li`), repositories live on "knots" (servers anyone can run), and what people do (a repository, a star, an issue, a profile) is a record kept on their own AT Protocol server. Forgeline reads it from Tangled's index at `api.tangled.org`, which gathers those records and answers XRPC queries about them, writes the signed-in person's own records (a star, a follow) to their own server, and a repository's issues, pull requests and comments to its knot. The client is `forge/tangled`, as `ForgeType.TANGLED`.

## What works

### Signed in

- **Signing in:** "Tangled" on the sign-in screen, with the account's handle and an **app password**. Tangled accounts are AT Protocol accounts (a Bluesky account is one), so the app opens an AT Protocol session with the account's own server (its PDS, found from the handle's DID document: `plc.directory` for `did:plc`, `/.well-known/did.json` for `did:web`) with `com.atproto.server.createSession`. Accounts on Bluesky's own servers (`*.host.bsky.network`) sign in at its entryway, `bsky.social`. The app keeps the session's access token (a JWT, whose `sub` says whose it is and so which server to write to) and its refresh token, and renews it with `com.atproto.server.refreshSession` as it does a forge's OAuth token. The password itself isn't kept.
- **Stars:** starring writes an `org.tangled.feed.star` record (`subject: {$type: "org.tangled.feed.star#repo", identity: <repository DID>}`) to the person's server; whether a repository is starred is asked of the index (`org.tangled.feed.getStar`), and unstarring deletes the record it names. A star given moments ago that the index hasn't read yet is found among the person's own records (`com.atproto.repo.listRecords`). Stars given with Tangled's former web app (`sh.tangled.feed.star`) are found and taken back the same way.
- **Following:** an `org.tangled.graph.follow` record keyed by the DID followed (`putRecord`), as Tangled's web app writes it; `org.tangled.graph.getFollow` says whether there's one.
- **Someone's stars:** `org.tangled.feed.listStarsBy`, each repository then looked up by its DID (`org.tangled.repo.getRepoByRepoDid`) and its owner's handle read from their DID document.
- **Issues and pull requests:** opening one, editing it, commenting, editing and deleting a comment, reacting, closing (an issue as done, `completed`, or as not planned, `closed`) and reopening, labels (and making a new one) and assignees. Opening a pull request writes its ticket, then its patch (`org.tangled.review.submitPatch` on the knot) from the head branch's tip and where it left the base branch; a patch the knot refuses takes its ticket away again. A review is a comment: Tangled has no verdicts nor remarks on lines yet.
- **The Feed:** Tangled's timeline (`org.tangled.feed.getTimeline`) as the person sees it, of the people they follow: stars, new repositories and forks. Follows are left out, as on the other forges. Since 2026-11-18 the index answers it only to them: each page is asked with a service-auth token their own server signs for that one call (`com.atproto.server.getServiceAuth`, addressed to `did:web:api.tangled.org`), as Tangled's web app does.

These follow what Tangled's own web app writes (`web/src/lib/api/graph.ts`, `write.ts`, `cob.ts`, `ticket.ts` and `pullCompose.ts` in `tangled.org/core`, read 2026-11-02 and 2026-11-17).

#### How writes reach a knot

Tickets (`org.tangled.track.ticket`), comments (`org.tangled.feed.comment`), reactions (`org.tangled.feed.reaction`) and label definitions (`org.tangled.label.definition`) aren't kept by their author: they are records of the repository, kept by its knot (`knot1.tangled.sh`, as the index names it) under the repository's own DID. To write one, the app:

1. asks the person's own server for a service token good for one minute and one call (`com.atproto.server.getServiceAuth`, `aud` the repository's DID, `lxm` the call: `com.atproto.repo.createRecord`, `putRecord` or `deleteRecord`);
2. makes that call on the knot with it. A rewrite names the version it read (`swapRecord`): if someone changed it in between, the knot refuses (`InvalidSwap`) and the app says so (`ForgeError.Conflict`);
3. attests what was written on the person's own server (`org.tangled.graph.attestation`, naming the record and its version), as the web app does.

A comment, a reaction or a label on a ticket names the version of the ticket it answers (a strong reference, read first with `com.atproto.repo.getRecord` on the knot). The knot adds who wrote each version as `x-tngl-editor`, which the index serves as `editor`: that is how the app tells whose comment or reaction it is. A label definition's key is made from its name (`Good first issue` is `good-first-issue`): the knot refuses another kind of key. Who may do what is reckoned as Tangled's web app does (`access.ts`): the owner administers, collaborators (`org.tangled.repo.listCollaborators`) push, and anyone may open and comment.

### Without an account

As Tangled serves everything it holds publicly:

- **Trending:** Tangled's own trending repositories (`org.tangled.actor.getTrending`, as many as it gives), mixed into the Trending page and shown whole: Tangled already picked them, so the page's star floor doesn't apply to them (`ForgeType.curatesTrending`). Tangled doesn't say for which period, so what each gained today, this week or this month is counted from its stars' dates (`org.tangled.feed.listStars`), for the row's count and its place on the mixed page.
- **Repositories:** description, website, topics, stars and forks, languages, README, files and folders, any file, branches and tags. The handle is resolved to a DID (`com.atproto.identity.resolveHandle`, on Bluesky's public AppView, which resolves any handle), the repository found by owner and name (`org.tangled.temp.repo.getRepoByName`), and its git read by the repository's own DID (`org.tangled.temp.git.getTree`, `getBlob`, `listBranches`, `listTags`). Since 2026-11 the index serves every repository as an `org.tangled.repo.manifest` record kept under that DID (`at://<repository DID>/org.tangled.repo.manifest/self`), naming the repository and its owner in `declaration`; former `sh.tangled.repo` records, kept by the owner and naming the DID as `repoDid`, are still read.
- **People:** a profile's description, location and links (its record asked by its own address, `at://<DID>/org.tangled.actor.profile/self`: the index refuses a bare DID), who follows them and whom they follow (counts), and their repositories.
- **Pictures:** found as Tangled's own avatar service finds them (`avatar/src/index.js` in `tangled.org/core`, read 2026-11-05): the blob the person's Tangled profile names (`avatar`, or `avatarCid` in the index's views), served by their own server (`com.atproto.sync.getBlob`), or else their Bluesky picture (`app.bsky.actor.getProfile` on Bluesky's public AppView). Tangled's web app serves them through signed addresses (`avatar.tangled.sh/<signature>/<DID>`) that only it can make. Shown on profiles, a repository's owner, Trending and the signed-in account.
- **Issues and pull requests:** one numbering for both, as on GitHub: a ticket's record key is the number the web app shows (`at://<repository DID>/org.tangled.track.ticket/4786` is `tangled.org/core/issues/4786`), and a pull request is a ticket with a target branch. Lists come from the index (`org.tangled.repo.listIssues`, `listPulls`; a closed pull request is one closed or merged, which the index calls `completed` since 2026-11-18 though its lexicon still says `merged`: the build adds it to the lexicon ozone is handed), words to find from its search (`org.tangled.search.query`), one ticket from `org.tangled.track.getTicketView`, its comments from `org.tangled.feed.listComments` and reactions from `org.tangled.feed.listReactions`. Labels are named by the repository's definitions (`org.tangled.label.listDefinitions`), which tickets only name by key.
- **A pull request's change:** its latest patch (`org.tangled.temp.review.listPatches`, which no lexicon describes yet) says from which commit to which, and from which repository and branch. The index's mirror of the knots diffs them (`sh.tangled.git.temp2.getDiff`, as Tangled's web app does since 2026-11): it holds a repository's objects and a fork's together, where the repository's own knot doesn't have a fork's head. It answers which lines changed by their numbers only, without context: the app reads both sides' text from the index (`getBlob`) and writes out the unified diff the file view shows, with git's three lines of context, as Tangled's web app does (`repoDiff.ts`). A binary file, a submodule or one over 1 MB is listed without it. Its commits come from `org.tangled.temp.git.listCommits` (`base..head`), and its checks from the repository's spindle (`org.tangled.ci.queryPipelines` on `spindle.tangled.network`, as the repository's manifest names it): the workflows of the latest pipeline run on its head.
- **History and blame:** a branch's or a file's commits from the knot (`org.tangled.git.listCommits`, paged by the last commit given), one commit with its change (diffed by the mirror against its parent, or git's empty tree for a first one), and who last changed each line (`org.tangled.git.getBlame`).
- **Search:** issues and pull requests (`org.tangled.search.query` over tickets), repositories (over their manifests) and people (`org.tangled.actor.searchActorsTypeahead`, by the start of a handle: one page).
- **Links:** `tangled.org/<handle>`, `tangled.org/<handle>/<repo>`, a file's page (`/blob/<ref>/<path>`) and an issue's or a pull request's (`/issues/12`, `/pulls/12`) open in the app; `@handle` works too.

## What doesn't, yet

| Need | Why | In Forgeline |
|---|---|---|
| Sign in through the browser | Tangled's web app signs in with AT Protocol OAuth, which asks a native app for a client metadata document served from a web address of its own (the client ID) and DPoP-bound tokens | An app password instead |
| Merging a pull request | Tangled merges through `sh.tangled.git.mergeCommit` on its own service, which no published lexicon describes yet | "Merge" isn't offered; the pull request opens in the browser for it |
| Review verdicts, remarks on lines | Tangled has none yet (`org.tangled.review.unspecced.round` is unused by its web app) | A review is a comment |
| An issue's or a pull request's events (who closed, labelled, assigned) | The index keeps a ticket's versions (`org.tangled.repo.listRecordVersions`) only as raw repository blocks | The timeline shows comments |
| Releases | Tangled has tags with notes, not releases | The tab is hidden (`RepoDetails.listsReleases`) |
| CI (spindles) | A spindle lists pipelines by commit, and serves their logs as a stream of its own | A pull request's checks; no Actions tab |
| Inbox | Tangled's notifications come from a service of its own (`org.tangled.temp.notification.*`) no lexicon describes yet | Not offered |
| Milestones, locking, pinning, drafts, what is asked of someone (Work) | Tangled keeps none of them | Not offered |
| Watching | Not in the index | Not offered |
| Display names | Tangled's profile record has none | The handle is shown |

## Where it comes from

The client's XRPC calls, and the shapes of what they answer, are generated by [ozone](https://github.com/christiandeange/ozone) from the lexicons in `forge/tangled/lexicons`: Tangled's own (`lexicons/org/tangled` in `tangled.org/core`, and the mirror's `sh.tangled.git.*` in `lexicons/git`) and the AT Protocol's (`com.atproto.*`, from `bluesky-social/atproto`), so signing in, stars and follows on a person's own server go through the same generated client as the reads. `tools/specs/fetch.py` (or the "API specs" workflow) refreshes them: a field Tangled renames then shows in the diff, and as a compile error. Only the methods listed in `forge/tangled/build.gradle.kts` are generated, with what they refer to. The records Tangled's index embeds as `value` (a repository, a ticket, a profile, a star) are typed `unknown` in its lexicons, since it serves former `sh.tangled.*` records alongside current ones: those are still read leniently by hand (`TangledModels.kt`).

Two of ozone's habits are worked around as the lexicons are prepared (`workAroundOzone` in the build file): a string kept as a definition of its own (`org.tangled.track.ticket#ticketState`) is written where it is referred to, as ozone generates no type for it, and a description holding a slash and a star (`refs/cobs/…`) has its star changed, as ozone writes descriptions into KDoc as they are.

Several queries are still under `org.tangled.temp`, which Tangled may rename: `TangledLiveTest` (run nightly with the other live tests) reads `tangled.org/core` (its issues, pull requests, their change and checks, its history and blame), Trending and search, and the Feed when the job has an account (`TANGLED_LIVE_HANDLE`, `TANGLED_LIVE_APP_PASSWORD`; skipped without), and fails when one moves or when the index answers something its lexicons don't promise. The fixtures the API tests read (`forge/tangled/src/test/resources/tangled`) are the index's, the knot's and the spindle's own answers, captured 2026-11-17. The writes aren't checked live: that needs an account's app password as a repository secret.
